# Steam Tool 缺失数据来源调研报告

## 1. 基线与目的

- 整理日期：2026-10-07，北京时间。
- 代码基线：`f8b23a5`，正式数据契约 `schema_version=2.0.0`。
- 契约依据：[data_contract.md](data_contract.md)。
- 运行边界：[运行逻辑说明](Steam_Tool_Runtime_Logic_Notes.md)、[本轮实现任务书](../task/Steam_Tool_Codex_Task.md)。

本报告整理当前实现中尚缺来源或缺少可靠映射的数据，供下一轮调研和 API → Data Block 映射设计使用。结论来自仓库代码审阅；候选方向尚未经过新的官方资料核对或真实接口验证，不应直接当作可用接口清单。

“当前代码没有提供”不等于“Steam 不存在该能力”。调研需要分别回答：来源是否存在、当前凭据是否能使用、字段是否表达所需事实、如何证明结果完整、接入需要多少请求。

## 2. 缺口总表

P0 优先解决默认核心数据缺失；P1 解决必要块和集合证据；P2 完善展示与可选维度。

| 编号 | 优先级 | 字段或维度 | 当前行为 | 缺口性质 |
| --- | --- | --- | --- | --- |
| R1 | P0 | `Achievements.unlocked / completion_ratio`，默认模式 | 有定义时 total 已知，解锁数与完成率为 null，meta.state=partial；明细模式可计算 | 独立汇总来源尚未验证，且受默认不请求完整明细的约束 |
| R2 | P1 | `Market.availability` | 始终为 null；Store 请求成功时 Market 仍为 partial | 尚无可靠的地区购买/获取资格映射 |
| R3 | P1 | `Bundles.items` 及 Bundle 全部字段 | Games/Wishlist 的 Bundles 为 unavailable、items=null | registry 没有 Bundle 来源；App → Bundle 关联和价格范围均未定义 |
| R4 | P2 | `Ownership.owners[steamid].persona_name` | 有 ID 时保留字典 key，昵称为 null | 已有个人资料接口，但多拥有者查询与拼装没有接入 |
| R5 | P2 | `Playtime.platform` 的 0/-1/null 判定，尤其 deck | 正时长保留；确认支持且时间为 0 才填 0；明确不支持才填 -1；其余 null | 平台支持/发行证据不足，与游玩时间来源不同 |
| R6 | P2 | Library 的 `GameIdentity.app_type` | 只保留已有来源中的字符串类型，其他情况为 null；Library 不请求 Store | 集合来源类型映射未验证，不能猜数字枚举 |
| R7 | P1 | 家庭集合完整性、共享资格，以及家庭候选的本人时长 | 家庭源 complete=false；资格证据不足保留 null；未取得本人时长不算未玩 | 已有来源的完整性/主体证据不足，部分属于判定规则而非新接口缺失 |
| R8 | P2 | `Price.currency / initial / final` 的条件性缺失 | 已有 Store 来源；缺值保留 null，付费零价与免费分开 | 优先核实现有来源的返回条件，不是整个价格来源缺失 |

当前状态影响：

- R1 使有成就定义且未开启明细的 Games/Library 成就块缺少完整汇总，影响 Record 状态与 Library 成就 Coverage。
- R2、R3 是 Games/Wishlist 的必要块缺口；涉及这些记录时，即使其他请求成功，Record 仍可能为 partial。
- R4 的昵称缺失不等于拥有关系未知；当前拥有关系状态主要由三个布尔事实决定，不能为补昵称丢失已确认的 ID。
- R5、R6 的可选字段为空不必然使当前块降级。尤其 `coverage.playtime` 只统计 total 是否已知，不证明平台维度完整。
- R7 的家庭完整性限制会反映到当前 Library 的 Run 聚合；读取成功不等于整个集合已完整验证。

## 3. R1：默认成就解锁汇总

### 已有证据

[library.enrich_player()](../steamtool/scripts/library.py) 在默认模式下只使用有效 schema 中的成就定义数量，设置 `items=null`，不发送 GetPlayerAchievements。开启明细时，复用 schema 与玩家逐项记录，计算解锁数和完成率。

[get_schema_for_game.py](../steamtool/Ports/get_schema_for_game.py) 提供定义，不能单独证明本人解锁数量。[get_player_achievements.py](../steamtool/Ports/get_player_achievements.py) 提供逐项玩家记录。[get_user_stats_for_game.py](../steamtool/Ports/get_user_stats_for_game.py) 当前只解码自定义统计列表，没有向业务层提供成就汇总。

### 需要调研

1. 是否存在当前个人凭据可访问、直接返回某个 App 总成就数和本人解锁数的稳定来源？记录准确接口、版本、认证类型和字段定义。
2. 已有响应中是否存在尚未接入、可被正式资料和真实样本共同证明的汇总字段？不能用任意自定义 Stats 条目猜成就数量。
3. 候选来源是否仍返回完整逐项列表？“不把列表写进 JSON”与“不请求完整列表”必须分开，不能只减少输出体积就宣称减少请求开销。
4. 是否覆盖零解锁、部分解锁、全部解锁、无成就系统、玩家数据私密、schema 与玩家数据不一致等情况？
5. 是否能确认数据属于 `run.subject_steamid`，而非家庭成员、全局玩家或其他账号？

### 验收与决策

- 默认模式取得可靠 total/unlocked 后，`completion_ratio` 可按契约计算，同时保持 `items=null`；默认没有明细不能单独降级。
- 确认无系统才使用成对 -1。缺少玩家记录、权限拒绝或来源不存在不等于无系统。
- 与显式明细模式逐 App 对照计数，并记录请求数量、响应体积、成功范围和总耗时。
- 如果没有满足当前运行规则的汇总来源，调研结论应明确这一限制：继续保持未知，或另行讨论是否允许读取完整列表但只输出汇总。后者是运行规则变更，不能静默实施。

## 4. R2：地区购买/获取资格

### 已有证据

[get_app_details.py](../steamtool/Ports/get_app_details.py) 使用 AppID、语言和国家/地区查询 Store 详情；[market_and_price()](../steamtool/contracts.py) 可从已有 `release_date.coming_soon` 取得发行状态证据，但没有可获取资格映射，因此 availability 为 null。

详情成功不证明可购买。当前请求失败或数据缺失也不充分证明该地区不可获取，不能直接写 false。

### 需要调研

1. 哪个结构化来源能直接证明当前查询地区可购买或获取，而不是仅证明存在商店页面、价格或发行信息？
2. `cc` 等地区参数的实际作用和适用范围是什么？是否还依赖登录账号、账号地区或其他上下文？
3. 能否区分地区限制、下架、未发售、缺少购买选项、免费获取以及依赖其他产品才能取得等情况？
4. 预购/预载如何解释？若出现未发售但“可以买”的证据，应与现契约关于 `released=false && availability=true` 的异常组合一起评审，不能强行填入布尔值。
5. 候选来源采用什么认证方式？当前 `region` 是查询上下文，不能未经验证解释为账号真实商店地区。

### 验收与决策

- 对同一 App 在不同地区对照，保存能支持 true、false、null 的明确证据。
- 将“地区普遍不可获取”与“当前账号不可获取”分开定义；若现有布尔字段无法表达证据，先记录契约问题。
- 404、success=false、无价格、无页面或无购买按钮均不能单独作为统一的 false 规则。
- Games/Wishlist 共用同一映射；确认资格时保留相应 source、fetched_at 和错误关联。

## 5. R3：Bundle 关联、组成与价格

### 已有证据

当前 [registry](../steamtool/Ports/registry.py) 没有 Bundle 工具。[build_record()](../steamtool/contracts.py) 明确输出 `Bundles(meta.state=unavailable, items=null)`。因此当前缺的是完整来源链，不只是某个价格字段。

### 需要调研

1. 如何从目标 AppID 找到相关 Bundle ID？结果是完整关联集合，还是仅当前市场展示的部分推荐？
2. 如何取得 `bundle_id`、`name`、`included_apps` 和四个价格业务字段？确认来源中的 ID 类型，不能把 Package/Sub ID 当作 Bundle ID。
3. App → Bundle 和 Bundle → App 两个方向的数据是否一致？没有名称时能否仍保留全部已知 AppID？
4. 价格是否取决于地区、币种、登录账号或已拥有内容？如存在个性化价格，需要明确当前契约能表示的查询范围。
5. 是否能区分已确认没有相关 Bundle 的空列表，与关联来源未取得的 null？是否需要分页或存在数量上限？
6. 候选是否来自可稳定核对的结构化数据？网页展示可作人工对照，不能直接把爬虫 fallback 当成已批准实现。

### 验收与决策

- 使用没有 Bundle、有一个、有多个、包含名称未知 App、地区不可读、价格不可得等样本。
- 验证关联完整性和价格上下文；来源只返回部分集合时使用 partial，不宣称完整。
- `Bundle.price` 不含独立 Meta；来源由 `Bundles.meta` 表达。
- `included_apps` 的 key 始终为 AppID 字符串，名称缺失不删除 key。
- 不扩展 DLC/父 App 关系图，不把 Bundle 组成变成新的 App Graph 项目。

## 6. R4：拥有者昵称

### 已有证据

当前 [ownership()](../steamtool/contracts.py) 保存已取得的拥有者 ID；本人持有已确认时，也会保留本人的 ID。所有 `persona_name` 当前均为 null。

[get_player_summaries.py](../steamtool/Ports/get_player_summaries.py) 已存在：当前入参为一个 SteamID，解码后只保留对应玩家。家庭组接口当前只向业务层提供成员 ID，没有接入昵称字段。

### 需要调研

1. 现有 GetPlayerSummaries 是否支持所需的多 ID 查询、批量上限和部分成功语义？不能把当前单人适配器当成已经支持批量。
2. 是否可以先收集全批次不同拥有者 ID，再用少量请求补全昵称，避免按 App × 拥有者重复查询？
3. 实际可读昵称的权限与失败条件是什么？私密、不存在、返回缺失、部分玩家可读时如何处理？
4. 当前家庭来源是否有可复用且主体明确的昵称字段？如有，验证名字对应的是哪个成员 ID，不凭数组位置关联。
5. 需要新增何种来源元信息才能让昵称与拥有事实同时可追溯？复核 Ownership 的多来源 fetched_at 表达，不能伪造旧的采集时间。

### 验收与决策

- 优先复用现有个人资料 Port、registry 和运行内去重；只有证据支持时才扩展参数与解码。
- 完全可读、部分可读和完全不可读都保留已知 SteamID key；昵称为空不改写三个拥有关系布尔值。
- ID 保持字符串，不新增重复的 owner_id 或展示层字段。
- 记录多游戏共享同一拥有者时的实际请求数，以及多来源失败是否应影响块状态的明确规则。

## 7. R5：平台支持与 Steam Deck 语义

### 已有证据

本人游玩接口提供被当前 Port 接受的四种平台时间字段；Store 详情可提供 `platforms`。但两者是不同事实：没有游玩记录不能证明游戏不支持平台。

[playtime()](../steamtool/contracts.py) 的现规则为：正时长直接保留；明确不支持且无正时长时为 -1；时间为零且明确支持时为 0；其余 null。Library 当前不请求 Store，因此不能假定拥有完整的平台支持证据。

### 需要调研

1. 现有来源对 windows/mac/linux 的支持标志是否表达发行支持、当前可运行性，还是其他范围？
2. 各接口省略平台字段和返回零分别表示什么？能否确认零时长与支持状态，避免把默认填充值当作业务事实？
3. deck 的“支持或发行”如何解释？验证平台时间、设备使用和兼容性标志能否互相证明，不能把某个标志缺失自动解释为不支持。
4. 已有正时长与“不支持”标志冲突时如何处理历史支持变化或来源范围差异？保留原始时间事实，不覆盖成 -1。
5. 是否存在不会恢复全库 Store 扫描开销的可靠支持信息来源？新增请求必须与 Library 当前精简查询目标一起评估。

### 验收与决策

- 覆盖四个平台的正值、零值、-1、null，包含来源冲突和平台字段省略。
- 明确 `coverage.playtime` 仍按 total 判断，不能利用 complete=true 宣称所有平台信息齐全。
- 若 deck 的现契约含义无法匹配可靠来源，交付语义决策问题，保留 null；不猜 sentinel。

## 8. R6：Library App 类型

### 已有证据

[get_shared_library_apps.py](../steamtool/Ports/get_shared_library_apps.py) 保留上游 `app_type`，但没有冻结数字枚举的映射。[library.run()](../steamtool/scripts/library.py) 只接入字符串类型；本人库 Port 没有暴露类型字段；Library 不请求 Store。

### 需要调研

1. 当前家庭来源的 app_type 的真实类型、枚举定义、版本及未知值语义是什么？
2. 是否能由当前已批准来源确认 game/dlc/demo/software 等类型，且适用于本人库、家庭候选和不可读 Store 的 App？
3. 不同来源类型不一致时如何选取证据？明确来源优先级与缺失回退，不能按名称猜测。
4. 为获取类型是否必须逐 App 查询 Store 或其他来源？若是，交付成本评估，不直接恢复 Library Store enrichment。

### 验收与决策

- 已知类型转换为契约允许的开放字符串；未知数字保留未知，不建立未经验证的封闭分类。
- 独立 DLC AppID 保留为扁平记录；不新增 parent_app 或推断所属本体。
- 类型缺失与身份完全不可用分别处理，不为了补类型丢失已知 AppID 和名称。

## 9. R7：家庭范围、共享资格与本人时长

### 已有证据

家庭共享适配器设置 `max_apps=10000`，始终保留 `complete=false`，数量达到上限时标记可能截断。当前没有经验证的分页/完整性保证。

`include_family_licenses=true` 的本人库调用是已有补充来源，但代码仍标记 `family_parameter_live_verified=false`。历史读取成功不等于该参数覆盖语义已经完整证明。

当前 `merge_ownership()` 只在其他家庭成员持有已确认且排除原因可解释时，进一步判断共享资格。因此部分资格为 null 可能源于保守规则，并不意味着完全没有相关上游字段。

### 需要调研

1. 当前共享列表范围是否覆盖成员全部可共享 App，是否有分页、隐藏项、截断、地区或权限过滤？需要什么独立证据才能提升 complete？
2. `exclude_reason`、拥有者名单与本人共享资格如何对应？确认未知枚举、仅本人持有、双方持有、他人持有且被排除等情形。
3. 对仅本人拥有的 App，available_via_family 的契约语义及当前 null 判定是否需要明确？先解决语义，不为填布尔值盲目增加接口。
4. `include_family_licenses` 返回的是完整许可证补充、本人已借玩记录，还是其他范围？对照真实客户端与声明查询范围。
5. 未玩家庭候选是否存在可可靠取得的本人零时长证据？缺少记录不能填 0，不能把家人的时间当作本人时间。
6. 尚未导出的家庭 `rt_playtime` 的统计主体和单位是什么？确认前保持不进入本人 Playtime；不因为字段看起来像时间就接入。

### 验收与决策

- 对照本人持有、双方持有、已借玩、可共享未玩、被排除、未知排除值、空家庭、来源失败及可能截断等样本。
- 清单完整性、拥有事实、共享资格与本人时长分别出具证据，不能相互替代。
- 本人时长缺失仍计入 playtime_unknown_count；played/unplayed 比例只用已知时长分母。
- `complete=true` 最多证明声明接口范围，不能宣称全部历史 Steam 许可证完整。
- 探测使用现有只读调用与身份绑定，不改变 token 主体核对，不增加自动登录流程。

## 10. R8：价格条件性缺失

### 已有证据

独立 App 的价格已经由 Store 的 `is_free` 和 `price_overview` 接入。问题是部分查询缺少其中的价格业务字段，而不是没有任何价格来源。

### 需要调研

1. 地区、发行状态、获取方式或响应范围是否导致价格字段省略？需通过具体来源文档和样本确认，不从省略推断免费。
2. 已知付费、100% 折扣、永久免费和类型未知的四类是否能稳定区分？
3. 预购、下架或只通过其他产品获得的 App，现有 Price 的 type/currency/initial/final 能表达哪些事实？
4. 同一查询地区若出现不同币种，当前简单排序是否仍可解释？先确认查询上下文；本轮不引入汇率或跨币种总价。

### 验收与决策

- 免费必须由 type=free 的明确证据支持，其三个价格字段为 null；付费零价仍为 paid。
- 未知 final 排在已知价格之后，不能作为 0 排序。
- Price 与 Market.availability 独立取证，不能把没有价格等同于不可获取。
- 若确认当前来源无法覆盖某类价格，交付精确范围和降级方案，再评估新来源。

## 11. 建议调研顺序与交付物

1. **R1**：先确定默认汇总目标在“不请求完整明细”约束下是否可实现；不可实现也应形成明确证据和策略选择。
2. **R2、R3**：核实 Games/Wishlist 必要块，避免把长期 partial 错当运行器故障。
3. **R7**：复核核心集合和共享资格证据，区分源缺失与规则未定。
4. **R4**：优先确认现有资料接口的批量复用，避免新增重复请求。
5. **R5、R6、R8**：补可选维度和条件性缺失；所有逐 App 新请求先评估成本。

每项调研都应交付如下映射记录，而不只给一个 API 名称：

| 内容 | 必须回答 |
| --- | --- |
| 证据与日期 | 官方资料/协议出处、核对时间、接口版本；社区资料如使用必须另行标明 |
| 来源状态 | 仅候选 / 资料已核对 / 只读实测通过 / 已完成契约映射 / 证据不足或不可用 |
| 身份与上下文 | 当前凭据可否访问、目标主体、地区、语言、是否个性化；不假定所有端点使用同一种认证 |
| 查询关系 | 以 AppID、SteamID、Bundle ID 或集合为目标，批量方式、上限、分页与依赖 |
| 字段映射 | 精确响应路径 → 契约字段，类型与单位，null/false/0/-1 的证据 |
| 完整性 | complete 的证据与适用范围；如何识别截断、遗漏及失败空集合 |
| 失败和冲突 | 错误/权限/缺能力分别映射什么状态；跨来源冲突如何处理 |
| 成本 | 请求数、重试数、响应体积、耗时、对当前去重和调度的影响 |
| 验证材料 | 脱敏样本、可重复对照步骤、离线 fixture 和验收用例 |
| 结论 | 可直接接入 / 仅可降级使用 / 需运行规则或契约决策 / 暂不可实现，以及依据 |

调研优先从官方说明、已有 Port 和可核对的只读结构化响应开始。涉及真实账号的验证只采集必要字段并脱敏；凭据、完整账户结果和私人样本不写入本报告或公开仓库。真实样本的失败不能被包装成零值或空集合。

## 12. 接入边界

本报告是待调研清单，不修改正式数据契约，也不批准新增来源。后续接入复用当前 registry、executor、错误系统、限流、重试和运行内去重。

不将以下内容扩展为本轮调研主体：Stats Feature、账户总消费、购买历史、DLC/Parent-App 图关系、完整 Steam App Graph、新缓存架构、爬虫 fallback、GUI 或 Web UI。

认证过期、未配置 Key/token、账号隐私与真实接口拒绝属于运行访问条件，需要单独定位；它们不自动证明数据来源不存在。源已存在但 Port 丢弃字段、Runner 未调用或契约判定未冻结，也应明确标为映射/接入/决策问题，不能统称“缺 API”。
